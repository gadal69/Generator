# 실행 로직 1차 수정 — 2026-10-25

최신 변경과 검증 범위는 [범용 검증·통합 검사·복구·중단/재개](UNIVERSAL_VERIFICATION_AND_RECOVERY.md)에 정리했습니다.

후속 함수 검증 기능은 `FUNCTIONAL_VERIFICATION_UPDATE.md`를 참고하세요. 아래 내용은 1차 수정 당시의 범위입니다.

## 변경 내용

- 기존 분석 확인 → 구현 → QA/재작업 → 최종 승인 흐름과 화면 디자인을 유지했다.
- 비서실장 분석에 `task_assignments`와 `acceptance_criteria`를 추가했다. 작업별 담당자·파일 소유권·인계 산출물·합격 기준을 전달한다.
- 디자인 담당자도 배정된 UI 코드 파일을 구현할 수 있다. 파일 소유권을 배정받지 않은 담당자는 해당 역할의 인계 자료를 작성하며, 전체 프로그램을 중복 구현하도록 지시하지 않는다.
- 중복 파일 소유권·존재하지 않는 담당자·명시된 요청 외 파일은 계획 검증에서 오류로 알린다. 모델이 잘못 만든 계획을 임의로 승인한 것으로 처리하지 않는다.
- 단순 GUI 파일 요청을 키워드 `UI`만으로 별도 디자인 담당자에게 자동 배정하던 규칙을 줄였다.
- 코드 생성·인계·QA의 응답 형식을 분리했다. QA는 해당 작업 범위만 검토하며 코드를 다시 구현하지 않도록 했다.
- 규칙 QA 선택은 실제로 모델 QA를 호출하지 않는다. 규칙 검토 통과는 기능 검증 미실행 경고를 포함한다.
- 누락/중복/다른 경로의 파일, 빈 응답, Python 문법 오류, 명시적으로 금지한 eval/exec의 직접 사용·별칭 import, 닫히지 않은 artifact 및 제공자가 보고한 응답 중단을 차단한다. 이는 정적 검사이며 일반적인 보안 증명이나 샌드박스는 아니다.
- 재작업은 최초 작업 지시를 기준으로 생성한다. 다음 담당자의 의존 관계는 QA를 통과한 수정본으로 연결한다.
- 실패 실행도 프로젝트의 `team_run_result.json`에 결과와 오류를 저장한다.
- 저장 파일 검증 실패 시 승인을 중단한다. 실제 실행/기능 검증이 미실행인 코드 산출물은 자동 최종 승인 대신 대표 수동 확인을 요구한다.
- Ollama/vLLM 응답의 종료 사유·토큰 통계 등을 새 `model_responses` 테이블에 기록한다. 원시 프롬프트나 API 키는 이 테이블에 저장하지 않는다. DB 마이그레이션은 기존 데이터 보존 방식으로 버전 3을 추가한다.
- Ollama 연결 확인 시 설치된 생성 모델을 기존 모델 목록에 추가한다. capabilities가 알려진 임베딩 전용 모델은 신규 선택지에서 제외한다.

## 모델 변경

모델 이름을 기준으로 실행 흐름을 분기하거나 특정 Gemma 모델의 출력 형식에 의존하지 않는다. 현재 설정은 유지했으며, 모델은 화면에서 선택하거나 `config/app_config.json`의 `ai.default_model`로 지정한다. Ollama/vLLM 서버가 해당 모델과 API를 지원하고 모델이 설치되어 있어야 한다. 모델별 품질·메모리·속도·출력 한도가 동일함을 보장하는 변경은 아니다.

필요한 경우 `ai` 아래에 선택적으로 모델별 설정을 추가할 수 있다. 기본값을 바꾸지 않아도 기존 설정으로 실행된다.

```json
{
  "model_profiles": {
    "gemma4:12b": {
      "ollama": {
        "timeout": 600,
        "options": {"num_ctx": 8192, "num_predict": 8192},
        "stages": {
          "implementation": {
            "retry_options": [{"num_predict": 12288}]
          },
          "qa": {"options": {"num_predict": 2048}}
        }
      }
    },
    "other-model-name": {
      "vllm": {
        "options": {"max_tokens": 8192, "temperature": 0.2}
      }
    }
  }
}
```

위 객체를 `ai.model_profiles`로 넣는다. 예시는 자동 적용하지 않았다. 예산을 늘리면 실행 시간과 메모리 사용량이 증가할 수 있다. `request_options.think`(Ollama), `request_options.chat_template_kwargs`(vLLM)는 서버·모델이 지원함을 확인한 경우에만 명시적으로 설정한다. 모델 이름만 보고 thinking 옵션을 추측해 전송하지 않는다.

공통 단계 설정은 `ai.generation.analysis`, `ai.generation.implementation`, `ai.generation.qa`에 `options`, `timeout`, `retry_options` 형식으로 추가할 수 있다. 적용 우선순위는 기본 설정 → 해당 모델의 제공자 설정 → 공통 단계 설정 → 해당 모델의 단계 설정이다. 제공자별 토큰 옵션 이름은 구분해야 한다.

## 검증

표준 라이브러리 unittest 기반 회귀 테스트 25개 통과. 운영 DB와 분리된 임시 DB/파일만 사용했다.

```powershell
.\.venv\Scripts\python.exe -B -m unittest discover -s tests -v
```

검증 범위: 임의 모델 이름 전달, Ollama/vLLM 응답 중단 처리, 단계별 모델 설정, 디자인 담당자의 코드 소유권, 중복 배정 차단, 규칙 QA의 모델 호출 방지, 문법 실패 후 재작업, 통과한 수정본 인계, 실패 기록, 기능 미실행 코드의 자동 승인 방지, 기존 DB 보존 마이그레이션 등.

추가로 Qt 화면 생성·데이터 조회·새 설치 모델 표시·합격 기준 표시, 기존 오프라인 전체 점검을 확인했다. GUI 검증 중 운영 설정 파일이 변경되지 않았음을 확인했다.

## 남은 검증과 한계

- 실제 Gemma 모델로 수정 후 계산기 생성 전체 흐름을 재실행한 결과는 아직 없다. 모델 이름을 바꾼 회귀 테스트는 제어 가능한 응답을 사용하는 오프라인 테스트다.
- 생성된 프로그램을 실행할 격리 환경과 신뢰 가능한 기능 테스트 실행기는 이번 변경에 추가하지 않았다. 실제 실행과 기능 테스트는 미실행으로 명시하며 수동 검증이 필요하다.
- 진행률·취소 버튼 등 새로운 화면 기능은 추가하지 않았다.
- 이미 열린 프로그램은 이전 코드를 사용하므로 종료 후 다시 실행해야 한다. 기존 운영 DB는 다음 실행 시 새 테이블이 추가된다.
