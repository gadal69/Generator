# QA 역할·최종 판정·실패 복구 규칙

| 단계 | 확인 범위 | 통과의 의미 |
|---|---|---|
| 로컬 QA | 배정 범위, 요구사항, 코드 논리, 산출물 형식 | 코드 검토 의견. 전체 실행 성공을 의미하지 않음 |
| 선택적 Gemini | 생성 코드의 독립 검토 및 수정 제안/수정본 | 추가 코드 검토 의견. 수정본도 로컬 QA와 실행 검사를 다시 거침 |
| 실제 실행 검증 | 대표 확인 기준에 따라 Docker에서 기능·파일 연동·DB·GUI·이미지 관측 | 지정한 검사 범위의 실제 결과 |
| 화면 검토 | 외관·가독성·잘림·배치 등 화면 품질 | 자동 위젯 이벤트 검사와 별개. 증거가 없으면 NOT_RUN |

Gemini는 옵션이 켜져 있고 프로젝트·목적·전송 범위가 일치하는 별도 외부 전송 승인이 있을 때만 사용한다. 일반 클라우드 승인 생략 설정이 있더라도 Gemini 코드 QA는 승인을 요구한다. 생성 시점에 승인하고 실제 전송 직전에도 재확인한다. 요구사항·코드는 기존 마스킹을 거친다. 마스킹이 모든 민감정보 제거를 보장하지는 않으므로 승인에 명시한 전송 범위를 확인해야 한다.

## 최종 판정

- 로컬/Gemini 의견이 PASS여도 필수 실행 FAIL을 덮어쓰지 않는다. Gemini FAIL 역시 수정 대상이다.
- 필수 검사가 생략·비활성·실행 불가·기준 미확정인 경우 NOT_RUN이며 최종 승인을 차단한다. 필수가 아닌 미검증은 별도로 표시한다.
- 파일 단위 QA에서 통합 단계로 미룬 검사는 실행 통과로 처리하지 않는다. 저장된 전체 파일을 다시 검증한다.
- 최종 승인에는 같은 결과·같은 파일 해시·같은 검증 계약·같은 환경의 증거가 필요하다. 수정 후 과거 PASS를 재사용하지 않는다.
- 최종 결과에 대한 재검증 FAIL/BLOCKED는 PENDING 및 APPROVED 승인을 INVALIDATED로 변경하고 프로젝트를 BLOCKED로 전환한다. 이후 PASS가 나와도 옛 승인을 자동 복원하지 않는다.

## 재작업과 중단·재개

실패한 요구사항·관측 결과를 바탕으로 담당 파일만 수정하며, 같은 실패가 반복되면 구현 접근을 바꾼다. 검증 기준을 완화하거나 예상 답을 하드코딩해서 통과시키지 않는다. 파일 작업과 통합 재작업은 기존의 각 한도를 유지한다. 한도 도달 시 REPLAN_REQUIRED로 중단하고 원인과 다음 조치를 안내한다. 한도 소진을 일반 중단·재개로 초기화하지 않는다.

체크포인트의 `qa_audit`는 검토/통합 단계, 실패 근거, 결과 ID, 이전·현재 해시, 실제 변경 줄 수와 제한된 diff, 재검사 결과와 Gemini 의견을 기록한다. 원인을 단정할 수 없으면 실제 관측 근거만 남긴다. `projects/<id>/qa_recovery.json`에 읽기 쉬운 이력을 별도 저장하며, 한도 도달 시 `final_result.txt`와 오류 메시지에 다음 조치를 표시한다. 이 기록은 로컬 저장이며 별도 외부 전송을 수행하지 않는다.

사용자 중단과 일반 오류는 기존 체크포인트에서 재개한다. 받아들인 코드와 미검토 결과를 재사용하되 필요한 QA·실행은 다시 수행한다. 요구사항·모델·검증 설정이 달라졌다면 새 분석이 필요하다. REPLAN_REQUIRED는 자동 재개하지 않으며 비서실장이 원인·인터페이스·분할을 재검토하고 대표 확인 후 새 실행을 시작한다.

## 검증 방식

정책 테스트에서는 모의 Gemini·로컬 PASS와 강제 실행 FAIL을 조합해 승인 차단을 확인한다. 옵션 꺼짐, 승인 없음, 범위 불일치, 전송 직전 승인 철회 상태에서도 전송이 일어나지 않는지 검사한다. 실제 Gemini API 전송은 이 테스트에서 수행하지 않는다. 중단·재개, 재작업 한도, 이력 보존과 실제 변경 기록, 승인 후 재검증에 의한 무효화도 회귀 검사에 포함한다. 개발기 디자인은 변경하지 않았다.
