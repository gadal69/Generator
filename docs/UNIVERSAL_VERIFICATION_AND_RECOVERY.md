# 범용 검증·통합 검사·복구·중단/재개

2026-10-26 추가 수정: 함수 사례의 `error: true`와 함께 `error_type: "TypeError"`처럼 정확한 예외 이름을 지정할 수 있다. 딕셔너리·목록 안의 숫자와 불리언도 타입을 구분하여 비교한다. [최신 실제 샘플 재검증](final_acceptance_20261026_round2/RESULT.md)에서 수정 전 오판 재현과 수정 후 검증 결과를 확인할 수 있다.

프로그램 생성 시스템의 공통 수행 로직을 수정했다. 계산기별 규칙이나 모델 이름에 따른 분기는 사용하지 않는다. 기존 화면 스타일은 유지하고 업무 지시 영역에 중단/재개 버튼과 단계·경과 시간을 연결했다.

## 수행 순서

1. 비서실장이 작업 분장과 검증 계약을 제안한다.
2. 대표자가 분석 화면에서 계약의 입력·예상 결과·필수 여부를 함께 확인한다. 사용자 입력에 명시한 계약이 모델 제안보다 우선한다.
3. 담당자는 배정 파일만 작성한다. 정적 검사와 파일별 가능한 검증 후 QA를 수행한다.
4. 승인된 담당 산출물을 묶어 전체 계약과 요구사항별 검증 범위를 검사한다. 여러 파일이 필요한 Docker 검사는 이 단계까지 보류한다.
5. 실패한 파일 담당자에게 한도 내에서 재작업을 요청한다. 수정 후 전체 계약을 다시 검사한다. 담당자가 없거나 반복 실패하면 `REPLAN_REQUIRED`로 멈춘다.
6. 저장된 파일을 다시 검사한 뒤 대표 최종 승인을 요청한다. 필수 검사 실패는 승인을 차단하고, 미실행 검사는 자동 승인을 차단한다.

모델 QA의 PASS가 실행 검사 실패를 덮어쓸 수 없다. 범용 검사는 명시된 사례와 조건의 충족을 확인하며 모든 입력에서의 정확성을 증명하지 않는다. GUI·외부 API 등 지원되지 않는 검사는 `NOT_RUN`으로 남는다.

## 검증 계약 예시

대표자 요청에 다음 블록을 넣거나, 비서실장이 제안한 계약을 분석 화면에서 확인한다. 모델 제안은 확인 전까지 `PROPOSED`이며 검증 통과 근거로 사용하지 않는다.

```text
src/Rules.py와 settings.json 파일을 작성해 주세요.
[검증 계약]
{
  "version": 1,
  "requirements": [
    {"id": "normalize", "description": "공백 제거 후 이름을 소문자로 바꾼다"},
    {"id": "settings", "description": "로컬 모드를 기본값으로 쓴다"}
  ],
  "checks": [
    {"id": "name", "kind": "python_function", "target": "src/Rules.py",
     "function": "normalize_name", "requirements": ["normalize"],
     "cases": [{"args": ["  Alice  "], "expected": "alice"},
               {"args": ["BOB"], "expected": "bob"}]},
    {"id": "mode", "kind": "json_value", "target": "settings.json",
     "path": ["mode"], "expected": "local", "requirements": ["settings"]}
  ]
}
[/검증 계약]
```

지원 검사: `file`(존재), `text`(contains/not_contains/equals), `json_value`(경로의 값), `python_function`(입력별 예상 반환값/오류), `command`(격리 프로세스 종료 코드/출력). `required` 기본값은 true다. 알 수 없는 종류는 삭제하거나 통과 처리하지 않는다. 각 요구사항에는 필수 검사를 연결해야 하며 연결이 없으면 미검증이다.

기본 함수 검사는 제한된 AST 해석기로 동작한다. 생성 코드를 호스트에서 import/exec하지 않으며 애플리케이션 전체 실행으로 표시하지 않는다. 여러 파일의 import나 라이브러리가 필요한 함수는 `engine: "docker"`를 지정한다. Docker 함수 검사와 command 검사는 담당 작업별 검사에서 보류하고 전체 파일 묶음으로 수행한다.

## 격리 실행 준비와 현재 제한

현재 작업 PC에는 Docker 명령이 없어 실제 컨테이너 실행은 검증하지 못했다. 자동 테스트에서는 Docker 부재 시 `NOT_RUN` 처리, 격리 옵션, 호스트 명령과의 분리, 호스트에서의 예상값 비교를 확인했다. 실제 Docker 환경 검증이 추가로 필요하다.

실행하려면 Docker 엔진과 검토된 로컬 런타임 이미지를 준비한 뒤 `config/app_config.json`의 `verification.images`에 런타임 이름과 이미지 참조를 설정한다. 초기값은 비어 있다. 모델이 이미지를 선택하지 않으며 자동 pull/패키지 설치를 하지 않는다. 모든 이미지는 신뢰된 검사 진입점 실행을 위한 `python`을 포함해야 한다. Node 명령 검사라면 Python과 Node가 모두 있는 이미지가 필요하다.

예를 들어 준비한 이미지의 키를 `python`으로 설정했다면 다음 검사를 추가할 수 있다.

```json
{"id":"startup","kind":"command","target":"main.py","runtime":"python",
 "argv":["python","main.py"],"exit_code":0,"stdout_contains":["ready"],"timeout":10}
```

컨테이너는 네트워크 차단, 읽기 전용 루트와 입력, 비특권 사용자, capability 제거, PID/CPU/메모리/시간 제한으로 실행한다. 생성 코드가 쓰는 작업 사본은 임시 메모리 영역이다. 예상 결과는 컨테이너에 보내지 않고 호스트에서 비교한다. Docker 부재 시 호스트 실행으로 대체하지 않는다. 컨테이너 정리 상태를 확인할 수 없으면 통과시키지 않는다. 격리는 완벽한 보안 경계를 보장하는 수단으로 주장하지 않는다.

공식 옵션 설명: [Docker run](https://docs.docker.com/reference/cli/docker/container/run), [tmpfs](https://docs.docker.com/engine/storage/tmpfs).

## 복구와 재개

첫 실패는 해당 결함 수정, 같은 실패 반복은 배정 파일과 인터페이스를 유지한 구현 방식 변경, 새로운 결함은 이전 통과 항목까지 포함한 회귀 수정으로 분류한다. 한도 초과 시 재분석·작업 분할·모델 적합성 검토 권고를 체크포인트에 저장한다. 다른 모델이나 외부 서비스로 몰래 전환하지 않는다. 모델 변경이 필요하면 새 분석과 대표 확인을 거친다.

중단 요청은 모델 응답 대기를 빠져나오며 늦게 도착한 결과를 작업 결과로 저장하지 않는다. 이미 요청한 원격 HTTP 작업 자체는 제공자의 제한 시간까지 계속될 수 있다. 컨테이너 실행 중 취소하면 컨테이너 정리를 시도한다. 승인 확정 직전까지 취소를 확인하고, 승인 확정 구간이 시작되면 완료 상태를 유지한다.

체크포인트는 동일 DB에 저장된다. 취소 또는 일반 오류 작업을 재개하면 통과한 작업과 QA 전 생성 결과를 재사용한다. 요청·모델·실행/검증 설정·원본 파일이 바뀌면 재개를 거부한다. 재작업 횟수도 보존한다. 화면의 재개 버튼은 가장 최근 중단/오류 작업을 선택하며 기존 모델을 먼저 선택해야 한다. `REPLAN_REQUIRED`는 재개 대신 새 분석이 필요하다. 프로세스 강제 종료로 남은 RUNNING 작업의 자동 복구는 제공하지 않는다.

DB 마이그레이션 v4는 기존 테이블을 삭제하지 않고 `workflow_checkpoints`, `workflow_events`를 추가한다. 단계·경과 시간·재작업 전략은 이벤트로 기록하며 진행률을 임의의 백분율로 표시하지 않는다.

검증 명령(PowerShell, 프로젝트 폴더):

2026-10-25 최종 오프라인 회귀 검사: **82개 테스트 통과**. 실제 Qt 작업 스레드에서 모델 응답 대기 중 중단하고 버튼·모델 선택 상태를 복원하는 동작까지 포함한다. 현재 PC에서 Docker 실행 검사는 `NOT_RUN`으로 반환되는 것도 확인했다.

```powershell
.\.venv\Scripts\python.exe -B -m unittest discover -s tests -q
```

검사 대상에는 함수/텍스트/JSON, 여러 파일, 계약 권한, 미지원 검증, Docker 부재와 명령 분리, 통합 재작업 한도, 모델 대기 중 중단, 승인 작업 재사용, 변경된 설정의 재개 거부, 기존 Qt 화면 동작이 포함된다. 실제 Ollama/Gemma 모델 품질과 실제 Docker 실행은 이 오프라인 테스트 결과에 포함하지 않는다.
