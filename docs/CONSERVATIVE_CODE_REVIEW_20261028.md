## 1. [P1] 앞선 구성 파일 QA 실패가 최종 승인을 무효화하지 않음 — 재현 확인

위치: `app/qa/qa_manager.py:39`, `app/approval/approval_manager.py:39`.

두 파일 프로젝트가 최종 승인 대기 중일 때, 첫 번째 파일의 기존 채택 결과에 FAIL 재검토를 등록했다. 무효화 쿼리는 같은 task_id만 찾으므로 마지막 파일의 승인 요청은 PENDING으로 남았다. 최종 승인도 마지막 Task의 QA만 확인해 APPROVED가 됐다. 과거의 전체 실행 증거는 변하지 않아 새 QA 실패를 반영하지 못한다.

수정 방향: 최종 증거에 포함된 모든 구성 Task/Result와 현재 승인 간 연결을 유지하고, 채택된 구성 결과의 최신 FAIL/BLOCKED를 승인 요청·결정 양쪽에서 검사한다. 무관한 옛 폐기 결과의 FAIL까지 무조건 전파하지 않도록 정확한 결과 ID 연결이 필요하다.

## 2. [P1] 저장 폴더에 원래 있던 파일은 내용 변경을 승인 검사에서 놓침 — 재현 확인

위치: `app/qa/approval_evidence.py:22`와 `:27`.

현재 실행에서 쓴 written_files는 해시를 만들지만 폴더의 전체 파일은 경로 목록만 보존한다. 같은 프로젝트 폴더에 미리 남아 있는 old_helper.py가 있으면 내용 해시는 빠진다. 실제로 저장 시점에 함께 존재했던 해당 파일을 검증 후 수정해도 파일 목록이 같아 승인이 APPROVED됐다. 파일이 새로 추가되는 경우의 차단과는 다른 문제다. 현재 최종 실행 검증 묶음도 written_files 중심이므로 남은 파일을 포함한 실제 배포 폴더 전체를 검증한 것은 아니다.

수정 방향: 배포할 파일 목록을 먼저 확정하고 전체 해시·전체 실행 묶음을 일치시킨다. 잔여 파일을 임의로 지우기보다 별도 실행 디렉터리를 사용하거나 추가 파일을 명시적으로 차단한다.

## 3. [P1] 승인 이후 보고서 저장 실패 시 상태 불일치 — 장애 주입으로 재현 확인

위치: `app/orchestrator/team_runner.py:459` 부근의 승인→결과 저장 순서, `:475` 부근 예외 처리, `:1320` 부근 보고서 출력.

자동 승인이 DB에 반영된 직후 보고서 파일 저장에서 OSError를 발생시켰다. 결과는 approvals=APPROVED, projects=BLOCKED, workflow_checkpoints=ERROR였다. 사용자에게 실행 실패가 보여도 승인은 남는다. 실제 디스크를 손상시키지 않고 저장 함수에만 오류를 주입했다.

수정 방향: 승인 확정과 부수 보고서 출력 실패의 의미를 구분한다. 저장 실패를 반드시 승인 차단으로 정의한다면 승인 전 완료해야 하고, 승인 후 부수 출력 실패라면 이미 확정된 상태를 일반 실행 오류로 되돌리지 말고 보고서 재생성 상태로 관리해야 한다. 보고서 임시 저장·교체도 필요하다.

## 4. [P1] Gemini 전송용 마스킹에 누락 — 모의 문자열 재현 확인

위치: `app/orchestrator/team_runner.py:973`.

테스트용 가짜 문자열에서 따옴표 없는 API_KEY=..., Authorization: Bearer ..., 8자 미만 password="tiny"가 그대로 남았다. 승인 게이트 자체가 우회된 것은 아니다. 다만 승인 문구는 민감정보 마스킹을 안내하므로 사용자가 기대한 범위보다 실제 마스킹이 좁다. 실키나 실제 외부 전송은 사용하지 않았다.

수정 방향: 전송 전 검사기를 공통화하고 환경변수·헤더·URL 쿼리·짧은 비밀번호 등 형식을 보강한다. 마스킹 결과 자체를 전송 직전 확인할 수 있게 하고, 민감정보 탐지 시 전송 중단 정책을 둔다. 단순 정규식으로 모든 비밀을 제거한다고 보장하지 않는다.

## 5. [P2] 강제 종료 후 RUNNING 체크포인트 복구 경로 부족 — 코드 확인

위치: `app/orchestrator/team_runner.py:150`, `app/gui/qt_dashboard.py:1209`.

정상 사용자 중단과 예외는 CANCELLED/ERROR로 저장되어 재개된다. 반면 프로세스 강제 종료·전원 차단이면 RUNNING이 남을 수 있고, 재개 API와 GUI는 이를 제외한다. 정상적인 중단·재개 테스트만으로 이 경우까지 검증했다고 할 수 없다. 인터넷 단절이 항상 강제 종료를 만든다는 뜻은 아니다. 이번 검토에서는 실제 전원 차단 실험은 하지 않았다.

수정 방향: 실행 소유자·heartbeat·lease를 기록하고 살아 있는 실행과 유실된 실행을 구분한다. 프로세스 확인 없이 RUNNING을 무조건 ERROR로 바꾸면 중복 실행 위험이 있다.

## 6. [P2] GUI·이미지 실행 환경 사전 안내 누락 — 재현 확인

위치: `app/tools/dependency_preflight.py:166`.

사전 환경 확인이 command 또는 engine=docker만 선택한다. gui와 image_output만 포함한 계약에서는 점검 호출도 안내도 없었다. 실제 실행기는 환경이 없으면 NOT_RUN으로 차단하므로 통과 우회는 아니지만, 분석 단계 안내가 빠져 뒤늦게 검증이 멈춘다.

수정 방향: 모든 실행형 kind의 런타임 선택을 공통 함수로 통일하고 gui의 기본 runtime=gui와 이미지 검사의 Pillow 준비 상태를 포함한다.

## 버그와 구분할 기능 한계

- GUI 자동화는 PySide6/offscreen, ASCII 입력, 파일 선택 경로 주입 범위다. 한글 IME, 실제 Windows 대화상자, 드래그, 화면 외관은 검증하지 않았다.
- 이미지 검증은 지정 좌표의 RGB 기준이다. 지정하지 않은 영역·알파·애니메이션 프레임·전체 이미지 품질까지 보장하지 않는다.
- 검증 계약의 요구사항 분해나 예상 결과가 불완전하면 그 범위 밖 결함을 놓칠 수 있다. 화면 검토를 실제 수행한 증거가 없으면 NOT_RUN을 유지해야 한다.
- 최근 GUI 샘플 성공은 결정적 테스트 픽스처에 대한 검증기 통합 성공이다. 이전 로컬 모델이 만든 다중 파일 샘플의 전체 자동 개발 성공과 같지 않다.

우선순위는 1·2·3의 승인 무결성, 4의 외부 전송 보호, 5·6의 복구와 사전 안내다. 각 결함의 재현 사례를 실패 회귀 테스트로 고정한 뒤 수정해야 한다.
